# POLITIKA Engine — foundational outline

Status: first-pass architecture, 2026-10-27  
Target runtime: Unreal Engine 5.8.3  
Design emphasis: clear RTS command interactions and POLITIKA-specific mechanics  
Display requirement: 4K (3840×2160) desktop capability plus adaptive handheld/mobile layouts and performance

Planned primary target platforms: Linux, Windows, SteamOS/Steam Deck, and Android; consoles and Apple platforms may follow later. See [Platform Support and Portability Plan](PLATFORM_SUPPORT.md).

## 1. Goal and boundary

**Primary contemporary RTS reference:** [Tempest Rising — Engine Architecture Reference](TEMPEST_RISING_ENGINE_REFERENCE.md) records source-verified public Unreal Editor/API patterns, their limitations and optional POLITIKA translations. It is research guidance, **not** an alternative implementation roadmap or evidence that POLITIKA has implemented those systems. Follow this outline and the owning acceptance contracts when developing features.

The goal is a complete, polished real-time strategy game, not a reproduction of a proprietary engine. POLITIKA should use UE as its rendering, platform, editor, asset, and packaging foundation, with a game-specific RTS layer implemented primarily in C++ and UE authoring/configuration assets. C# remains suitable for external content/build tools where it earns its keep; it is not required in the runtime.

The game-specific layer needs to support faction/unit content, squad/vehicle combat, tactical objectives, campaign missions, skirmish and immediately prioritized multiplayer foundations, AI, maps, in-game briefings and dialogue, audio, save/replay, and localization. The economy, production, deployment, reinforcement and objective-control rules remain POLITIKA design decisions; this outline establishes systems capable of supporting those choices.

## 2. Proposed layers

Treat these as ownership boundaries and data flows, not necessarily separate UE modules. Start with a small number of runtime/editor modules and split only when build, ownership, or team boundaries justify it. The key contract is: **input becomes validated player commands; the match/simulation applies rules; state changes emit events; presentation observes those events.** UI, animation, audio, and VFX must not be the source of gameplay truth.

**Multiplayer architecture decision (2026-10-29):** [RTS Multiplayer Architecture](RTS_MULTIPLAYER_ARCHITECTURE.md) defines the **immediate implementation priority** for a server-authoritative, up-to-four-human model with interchangeable listen and dedicated server hosting. All existing and newly authored gameplay code must undergo the **mandatory full-code retrofit inventory and per-symbol authority/replication assessment** in that document (§2.1), including explicit fixes or justified no-change findings. Begin MP-0 code audit/retrofit **immediately**, then implement the smallest MP-1 two-client listen-server match and early MP-3 dedicated-server parity. **Update (29 October 2026): MP-0 audit complete and MP-1 implemented.** The [MP-1 acceptance record](RTS_MULTIPLAYER_FOUNDATION_ACCEPTANCE.md) covers the listen-server transport, connection-bound seats, team fog and 1v1/2v1/3v1/2v2 + Unaligned layouts; packaged two-process qualification is 1v1 only. MP-1 was prioritized before Stage 4B and needed only the narrow Stage 4A authority/lifecycle prerequisites, not Stage 4F completion. Offline play remains a permanent supported architecture. Historical Stage 3, Stage 4A, command-contract, navigation and infantry verdicts are unchanged. Matchmaking, online providers, reconnect, anti-cheat policy, save/replay and dedicated server builds are **not implemented**; public matchmaking/services remain later. Do not create a second simulator, separate duplicate applications or new Stage 4A–4F acceptance gates; MP-0 audit precedes any MP-1 two-client proof.

### Minimal RTS gameplay contract

Use the following **small set of shared gameplay concepts** to structure the engine. These are *responsibility and data-flow contracts*, not a demand for one class/module per noun or a new universal rules engine. C++ owns the authoritative interpretation, UE assets author reusable definitions, and presentation remains a consumer of permitted state.

| Core concern | Minimal contract | Immediate use / growth boundary |
|---|---|---|
| **Match and world** | One match context owns simulation time, its selected ruleset, participants, map, objectives and authoritative lifecycle. Map geometry, starts, blockers and legal regions belong to this context. | The existing prototype coordinator/map fixture is the initial case; standard skirmish slots and campaign rules are separate profiles, not prototype assumptions. |
| **Definitions and instances** | Versioned stable-ID *definitions* describe reusable unit/weapon/objective/movement types. A spawned *instance* has its own runtime identity and state and refers to a definition. Human-readable names, files and meshes are not gameplay IDs. | Move prototype unit/weapon values into typed assets first; preserve behavior. No generic entity database or mandatory custom base Actor hierarchy is implied. |
| **Participants and relations** | Keep a controller/decision-maker, playable slot, faction affiliation, entity owner, command authority, and diplomatic hostility conceptually distinct. Permission to issue an order is evaluated for the current state, not inferred from art or a fixed faction label. | Use the simple friendly/hostile prototype permissions now; retain the distinction for four playable factions and the separately controlled Unaligned NPC. |
| **State and constraints** | The simulation owns mutable position, health, current orders, capability/operational status, relationships and objective progress. A resource is a *typed, scoped* stock, flow, cost or capacity only when a mechanic actually requires it; owning a building is not the same as that building functioning. | Health, cooldowns and objective progress exist in the slice. Add economy, power, supply and contract accounting only alongside their implemented rules. |
| **Commands, processes and events** | A *command* expresses intent; validation admits or rejects it. An admitted command may start a time-consuming *process* with interruption/failure. Rules update state and emit *events* describing what occurred. Neither a click nor an animation is the authoritative effect. | Continue using the C++ typed-order/admission kernel and 20 Hz prototype simulation; expand behaviors incrementally, without a second simulator in Rust. |
| **Space and movement** | Legality depends on the intended movement profile, current passability/occupancy, allowed bounds, and the relevant target/interaction rule; static map connectivity is not the same as dynamic path success. | Version the prototype fixture and validate legal starts and movement-profile reachability; avoid assuming one universal walkable graph. |
| **Information** | *World truth* is distinct from the player/AI's permitted observation. Current sightings, remembered locations, intelligence claims and belief are different information kinds; claims may be stale or false without altering the world they describe. | No complete fog, intelligence, evidence or belief engine is needed for the first data/content milestone. Keep the API/ownership boundary so later deception cannot leak authoritative truth. |
| **Objectives** | Mission/victory logic evaluates explicit conditions over authoritative state and qualifying events, including identity and provenance where required. Player intentions, reports and visually indicated progress cannot independently satisfy an objective. | Retain the tested control-point fixture. Later distinguish producing an asset from buying, stealing, possessing or deploying it when defining specialized victory conditions. |

**Authoritative data flow:**

```text
Validated definitions + map/profile + participant setup
    -> admitted match -> authoritative world state

Human input / AI decision
    -> typed command request -> authority + target + rule checks
    -> accepted execution or explained rejection
    -> state transitions + recorded gameplay events

Authoritative state + access/visibility rules
    -> participant-specific observation -> HUD / AI decisions

State + qualifying events
    -> objective evaluator -> match progress / result
```

**Non-negotiable invariants for implemented features:**

1. **Identity is typed and stable.** An authored archetype ID is not a spawned instance ID; references must resolve under an explicitly supported content version. Failed required content validation blocks match admission, not merely editor warnings.
2. **There is one source of truth.** Only authoritative gameplay rules change health, position, resources, ownership/control or objective state. UI, animation, fog rendering and external tooling may request, display or test changes but cannot independently enact them.
3. **Commands are conditional, actions occur over time.** Every supported order is checked against current issuing authority and target/action constraints; a rejected order has no gameplay effect. Accepted actions can become invalid or be interrupted later, with explicit effects and feedback.
4. **Control is contextual.** Faction, player slot, unit ownership, controlling agent, mercenary rights and neutrality must not collapse into one assumed equivalence. The Unaligned is NPC-only and never an occupied playable slot in ordinary matches.
5. **Space is typed.** Position alone never proves start, movement, placement or target legality. Reachability checks name the movement class and endpoints, and distinguish authored static checks from dynamically changing routes.
6. **Information cannot rewrite reality.** Observation follows participant access; an unverified or fabricated report modifies recipient knowledge only. Rejection reasons and UI projections must not reveal hidden authoritative facts.
7. **Effects and goals are distinguishable.** Transfers, damage, destruction, control changes and production completion are different state transitions. Objectives use the event/state actually required (for example, *own production* is not *possession*).

**Immediate application:** the accepted [First RTS Vertical Slice](RTS_VERTICAL_SLICE_MILESTONE.md) already tests basic move/attack orders, entity state, combat events and a control objective. The next bounded increment should extract existing prototype unit/weapon definitions into stable-ID UE gameplay assets, author a versioned prototype map/profile with bounds/slots/starts/objective markers, and add actionable type/reference/value/spatial checks plus a cooked pre-match rejection path. Preserve current results. Do **not** pull harvesting, full production, intelligence/belief modeling, mercenary contracts, strategic AI, broad rosters or full campaign rules into this increment.

This contract consolidates the implementation-relevant distinctions from [RTS mechanics and simulation research](RTS_GAME_ONTOLOGY.md); it does not supersede the owning [Match Structure](MATCH_STRUCTURE.md), [Concepts Outline](CONCEPTS_OUTLINE.md), or the specific [map/content validation contracts](#map-authoring-contract-and-validation-pass) below. Keep the data model as small as the playable and negative-test fixtures actually require.

### Yugoslav setting: practical world-state boundary

The [Yugoslav World and Campaign Systems Model](YUGOSLAV_WORLD_MODEL.md) maps the common RTS contract to actual 1980s institutions, geography, infrastructure and POLITIKA's divergent 1984–1989 campaign. The **historical-world layer does not add another match faction or require a nationwide simulation**. Preserve these separations when corresponding content is implemented:

| Concept already used by the engine | Historical-world implication | First development obligation |
|---|---|---|
| **Spatial map and marker** | A bridge, border, industrial site, archive or relay has geometry *and potentially* a jurisdiction, service and access role. | The current fixture needs only bounds, legal starts, movement-class reachability and objective references; later region/access metadata is scenario driven. |
| **Entity, controller, faction** | A civilian, municipal service, JNA patrol, Territorial Defence unit and inner security cell may have different knowledge and instructions while remaining inside the NPC-only Unaligned faction. | Keep stable instance identity, authoritative ownership and order admission separate from future institution/mandate metadata. |
| **Operational state and process** | A site can remain owned while its power, delivery route, workforce or communications service fails. | Do not use ownership as a universal proxy for operability; model only implemented health/cooldown/objective values in the immediate slice. |
| **Observation, claim and evidence** | Newspaper, hospital record, intercepted dispatch, witness and fabricated broadcast are different evidential objects; a secret report may be false without changing real world state. | Keep observation/state authority separated. No new evidence, propaganda or belief engine in the next milestone. |
| **Event and objective** | Seizing a broadcast station, preserving its recordings, proving a death and transmitting corroborated evidence are distinct events and goals. | Retain simple control-point completion now; later objective predicates should use the correct state/event and provenance. |

**Two provenance boundaries:** the archive stores **developer-facing evidence about real history** (date, source and rights), while gameplay may eventually store **fictional in-world evidence and deception** (origin, custody, recipient, truth and verification). They must not share one overloaded provenance or truth flag. Historical appearance, real-world institutions and real protest histories require the [production review](PRODUCTION_STANDARDS.md) and [archive/source rules](../Archive/RIGHTS_AND_PROVENANCE.md); scenario specifics remain owned by [Story](STORY_OUTLINE.md) and [Concepts](CONCEPTS_OUTLINE.md).

**Current milestone protection:** map names, jurisdictions, public institutions, political behavior and campaign evidence are not required fields for the prototype map schema. Do not make the data-driven unit/weapon/map validation milestone depend on federal-government AI, a chronology engine, regional populations, self-managed enterprise economics or plot-specific clue puzzles.

| Layer | Owns / exposes | UE mapping and boundary |
|---|---|---|
| Platform & application shell | Process startup/shutdown, user/device settings, display and UI scale, input mapping, localization, save slots, platform services. Exposes initialized local-player services; owns no match rules. | `UGameInstance`/`UGameInstanceSubsystem` for process lifetime; `ULocalPlayerSubsystem` for per-player preferences/input; `UGameUserSettings`, Enhanced Input, `USaveGame`, and UE Internationalization APIs. Keep platform-specific services behind interfaces so headless/server targets do not depend on UI. See [Platform & application layer](#platform--application-layer) below. |
| Player interaction & presentation | Camera/navigation controls, selection and hover, command palette/HUD, menus, accessibility, audio/VFX/animation/cinematics. Converts gestures into command requests and renders a read-only projection of match state. | `APlayerController` and local-player subsystems for input/selection; camera pawn/components; UMG/CommonUI, Niagara, Audio, Sequencer. Never directly mutate health, ownership, resources, or objective state from widgets/Blueprint presentation logic. |
| Match orchestration & rules | Match phases and configuration; player/team/faction roster; command admission; objective and victory evaluation; pause/spectator policy; match start/end and results. Provides the authoritative context used by simulation and mode-specific rules. | `AGameMode` for server/standalone authority and setup, `AGameState` for shared match state, `APlayerState` for replicated player identity/score, plus focused match/rules subsystems. GameMode is not the home for every rule; campaign/skirmish variants should compose or select rule policies. |
| Command & simulation | Typed, validated orders (move, attack, attack-move, stop, guard, ability); ownership/permission checks; entity lifecycle; movement intent, targeting, combat resolution, health/status, cooldowns, resources, squad/member state, and simulation events. This is the gameplay source of truth. | C++ domain types and server-authoritative Actors/components first. Use fixed-step or explicitly scheduled systems where measurement warrants; make commands and state snapshots serializable. Keep simulation APIs callable without UI, and isolate cosmetic callbacks from state mutation. |
| World model, spatial queries & navigation | Playable bounds; terrain/buildability; occupancy/blockers; movement layers and costs; reachability; path requests/results; formations and local avoidance; line of sight; per-player vision, explored/shroud state, and detection/intel queries. | UE World/landscape and collision remain rendering/editor foundations. Add RTS-specific grid, sectors, or nav data for tactical costs, occupancy, visibility, and batch queries; bridge to UE NavMesh only where its semantics fit. Avoid making render meshes or fog materials authoritative. |
| Content schema & runtime content | Stable IDs and versioned definitions for factions, unit/squad archetypes, weapons, abilities, upgrades, structures, objectives, AI profiles, and rulesets; validation/migration and asset resolution. Definitions parameterize code-owned behavior; they do not contain hidden per-instance state. | `UPrimaryDataAsset`/Asset Manager for identity, loading, bundles, and references; DataTables/Curve assets for suitable bulk tuning. Validate IDs, references, ranges, and compatibility in editor/CI. Use Blueprint subclasses mainly for authored presentation and exceptional scripted composition, not duplicated core rules. |
| Mission, scripting & AI | Mission triggers/objectives/checkpoints/dialogue/event sequencing; strategic AI decisions (composition, deployment, objectives) and tactical coordination (orders, threat response, retreat). AI emits the same command types as players, subject to the same rules and visibility constraints. | Mission/rules services plus data-authored triggers or a constrained scripting interface; StateTree/Behavior Tree can orchestrate behaviors but should call simulation command APIs. Separate AI planning cadence from per-entity movement/combat updates and provide debug traces/overlays. |
| Networking, persistence & replay | Transport/session integration, authority and replication policy, reconnect/late-join if required; versioned save snapshots; replay recording/playback and diagnostics. Records canonical commands and relevant checkpoints/events, not presentation state. | UE networking/session APIs for transport and replicated state as appropriate; keep a transport-independent command/state contract. Choose server authority for conventional online play. Do not promise deterministic lockstep until cross-platform determinism is demonstrated; timestamped commands plus checkpoints are the lower-risk replay baseline. |
| Editor, validation & build pipeline | Map/faction authoring workflows, import/conversion, linting, balance iteration, localization checks, cook/package automation, and reproducible diagnostics. Fails early on invalid content and unreachable/illegal map setup. | UE Editor modules, asset validation/Data Validation, commandlets/automation, source-control hooks and CI. World Partition is conditional on demonstrated map scale/streaming needs, not a default RTS requirement. Keep third-party binary research and conversion utilities outside runtime dependencies. |

### Layering decisions and tool fit

- **Independence and provenance:** Implement POLITIKA-specific gameplay rules, architecture and content in owned source and Unreal Engine assets. External open-source RTS designs can inform general patterns only after license and provenance review; they are not runtime dependencies.
- **Asset inspection and tooling:** Use Ghidra, angr, ImHex and similar inspection tools only for narrowly scoped and legally permitted research when necessary. Do not incorporate proprietary assets, undocumented binaries or unrelated engine-specific formats into the playable product.
- **UE-native choices to prototype, not assume:** Epic's [MassEntity](https://dev.epicgames.com/documentation/unreal-engine/overview-of-mass-entity-in-unreal-engine?lang=en-US) uses data fragments, archetypes, and processors; [MassGameplay](https://dev.epicgames.com/documentation/en-us/unreal-engine/overview-of-mass-gameplay-in-unreal-engine) adds spawning, representation, movement, LOD, StateTree, signals, and Smart Objects. Evaluate it if profiling shows Actor/component overhead at target unit counts. Keep player-commanded/hero entities as Actors if that simplifies interaction, and use Mass selectively for numerous background/simulated entities only if integration and replication costs are acceptable.
- **Navigation and fog are separate contracts:** first prototype a coarse strategic path graph/grid with terrain costs and blockers, then local steering/avoidance; decide whether UE NavMesh is sufficient for the map and movement semantics. For fog, keep per-player visibility/exploration queries authoritative and treat textures/materials as presentation. A community [UE5 FogOfWar](https://github.com/zhmyh1337/FogOfWar) project is a candidate for inspection, not a production dependency until UE 5.8.3 compatibility, license, performance, multiplayer semantics, and maintenance are checked. The older [ue4-rts](https://github.com/npruehs/ue4-rts) is a useful end-to-end feature reference but targets UE 4.27/early UE5; do not assume it is current-engine compatible.
- **Technical references:** Prefer Epic's Unreal Engine documentation, engine APIs, instrumented POLITIKA prototypes and measured target-platform behavior over comparisons with individual commercial games.
- **Open-source RTS architecture study:** The local [Thyme study](THYME_ARCHITECTURE_STUDY.md) extracts typed behavior composition, command/update ordering, state ownership, and diagnostics from a Generals: Zero Hour reimplementation. Transfer the principles only; keep POLITIKA's UE/C++ implementation and rules independent, and observe the documented GPL boundary.

### Platform & application layer

This layer is the game's **shell and local-user services**, not a second gameplay framework. Its job is to turn a process launch into a configured local player and a loadable game session, then provide stable settings, input, localization, persistence, audio, and platform-service APIs for the rest of the game. It must remain usable in editor, standalone, packaged, and (where applicable) headless/server contexts.

#### Ownership and contracts

| Service | Owns | Initial UE implementation / contract |
|---|---|---|
| Application lifecycle | Startup options, startup failure/recovery, main-menu/session transitions, clean shutdown, command-line/URL arguments, crash-safe return to menu. | `UGameInstance` plus a small `UGameInstanceSubsystem` coordinator. Keep transitions explicit (`Boot → LoadUserSettings → ResolveProfile/OfflineMode → MainMenu → Session → Shutdown`) and make startup idempotent. No map-specific or match-rule state here. |
| Device/display preferences | Window mode, resolution, monitor, frame cap, VSync/upscaler/scalability preset, render scale. | Subclass `UGameUserSettings` for display/render settings; persist only supported values and call `ApplySettings` through a preview/confirm flow. Keep display resolution separate from logical UI scale and world-camera zoom. |
| User/profile preferences | User-facing preferences that follow a local profile (language, accessibility, audio mix/gains, camera behavior, UI scale, input bindings). Support a safe default profile and offline use. | A versioned settings object/service, optionally `ULocalPlayerSubsystem` for per-local-player state and `UEnhancedInputUserSettings` for rebinds. Do not make online identity/account credentials a prerequisite for launching a local campaign. |
| Input setup | Semantic actions, default mapping contexts, device/gamepad detection, remapping, conflict resolution, reset-to-default, and context priority (menu/gameplay/overlay). Emits player intent only. | Enhanced Input assets and `UEnhancedInputLocalPlayerSubsystem`; store user overrides separately from shipped defaults. Use action names such as `Select`, `AddToSelection`, `MoveOrder`, `AttackMove`, `Stop`, `CameraPan`, `CameraZoom`, `OpenMenu`, not raw key codes in gameplay code. |
| Save/profile storage | Slot enumeration, metadata, thumbnails, schema version, migration, corruption handling, async load/save, autosave policy, and platform user ID association. | `USaveGame` subclasses behind a save service; separate campaign/match snapshots from user settings and profile metadata. Use stable IDs, versioned payloads, async I/O for large snapshots, and recoverable temp/commit behavior. Never serialize widget, Actor pointer, or machine-path state as durable identity. |
| Localization/accessibility | Culture selection and fallback, localized text/audio assets, subtitle policy, font fallback, number/date formatting, text scale, color/contrast options, input prompts, and screen-reader hooks where feasible. | UE Localization Dashboard/Internationalization APIs and localized asset groups; resolve culture at startup before building the main menu, permit runtime language change only where assets/UI can safely refresh. Test diacritics and long-string expansion (important for South Slavic languages) at 4K and 1080p. |
| Platform adapters | Optional achievements, cloud saves, overlay/invites, entitlement/session identity, and platform shutdown callbacks. | A narrow `IPolitikaPlatformServices` abstraction with a no-op/offline implementation; adapt Steam/EOS or another provider only after release/platform scope is decided. Keep account/login, commerce, and online service failures recoverable and outside core settings/save serialization. |

**State separation is a hard rule:** device settings (machine/display/audio device), local-user settings (input/language/accessibility), account/profile data (if online is chosen), and game saves (campaign/match progress) are different stores with different lifetimes and migration rules. Gameplay systems read preferences through services but never write their own ad-hoc config files. A server target must not initialize local-player UI/input services.

#### POLITIKA settings and accessibility requirements

- **Action-oriented input:** Define semantic commands such as selection, movement, stop and group assignment. Persist rebinding by action, key, modifiers and device; validate conflicts and provide reset-to-default.
- **Typed settings:** Organize user preferences by graphics, audio, controls, localization and accessibility. Validate type, range, default and platform availability. Keep user preferences separate from balance parameters.
- **Explicit shell states:** Separate profile selection, save/load, video, audio and gameplay options without making online account creation a prerequisite.
- **Responsive layouts:** Use DPI, safe-area and controller/touch-aware scaling rather than a single fixed-resolution menu canvas.
- **Complete localization:** Check glyph coverage, South Slavic diacritics, font fallback, subtitles, culture formatting and text expansion under real target resolutions.

#### POLITIKA build order and acceptance

1. **Shell skeleton:** establish the UE-owned startup path, local/offline entry, early diagnostics, and recovery behavior before gameplay systems depend on it. Keep the runtime implementation in one C++ bootstrap contract; use engine config for defaults, not a second custom settings format.
2. **Settings contract:** build the typed device/profile stores and small Video, Audio and Interface settings pages described in [the Settings contract](#settings-contract-implementation-notes). Prove default/validation behavior, scoped backups/resets, migration/corruption preservation, and save/restart plus confirmed/reverted display-mode flows before generalizing settings to other gameplay systems.
3. **Input contract:** implement the semantic actions, phase-scoped Enhanced Input contexts, and per-profile remapping behavior described in [the Input contract](#input-contract-implementation-notes). Start with keyboard/mouse defaults; then deliver rebinding, actionable conflict reporting, reset, and device-correct controller prompts. Verify modal overlays suspend gameplay input and restore it without stuck/repeated actions.
4. **Persistence/localization:** implement the versioned save metadata, profile-scoped asynchronous save/load service, and localization/accessibility behavior described in [the Persistence and localization contract](#persistence-and-localization-contract-implementation-notes). Prove campaign migration is independent from profile/preferences migration, cultures fall back safely, and localized fonts/subtitles/accessibility settings work in packaged builds.
5. **Platform integration:** implement the offline-first service boundary and platform-scope gate described in [the Platform integration contract](#platform-integration-contract-implementation-notes). Prove that absent services, lost network, first-run state and invalid/corrupt local data cannot block local menu/campaign/skirmish entry before choosing or shipping an online provider.

**Acceptance gates:** boot to menu with no online dependency; defaults/reset are deterministic; invalid or old settings recover with a logged explanation; remapped bindings persist and conflicts are actionable; settings survive restart; language applies before UI construction and localized fonts cover Latin Extended diacritics; display previews can be reverted after timeout; saves enumerate/load/migrate without blocking the game thread; headless/server mode never constructs local-player widgets; all menus and text remain usable at the project's 4K baseline and supported lower/ultrawide resolutions.

#### Settings contract implementation notes

**Reference findings and transfer.** The extracted C&C4 APT interface contains separate main settings, general, video and audio screens. See the local [general-page resource](</mnt/data/CommandAndConquer/UM/Command and Conquer 4 Tiberian Twilight/extracted/Apt/data/aptui/shell_screen_settings_generalpage.manifest>), [video-page resource](</mnt/data/CommandAndConquer/UM/Command and Conquer 4 Tiberian Twilight/extracted/Apt/data/aptui/shell_screen_settings_videopage.manifest>) and [audio-page resource](</mnt/data/CommandAndConquer/UM/Command and Conquer 4 Tiberian Twilight/extracted/Apt/data/aptui/shell_screen_settings_audiopage.manifest>). The asset extraction is inventoried in the [C&C4 extraction record](</mnt/data/CommandAndConquer/UM/Command and Conquer 4 Tiberian Twilight/extraction-manifest.md>); it is shipped UI-asset evidence, not a live runtime observation. The [PCGamingWiki C&C4 entry](https://www.pcgamingwiki.com/wiki/Command_%26_Conquer_4%3A_Tiberian_Twilight) documents profile-scoped `Options.ini` separately from saved-game storage; [C&C3 documents the same profile Options.ini pattern](https://www.pcgamingwiki.com/wiki/Command_%26_Conquer_3%3A_Tiberium_Wars). Take the category grouping and profile ownership as useful precedents, not the flat file schema or account prerequisite. An [EA forum report](https://forums.ea.com/discussions/command-and-conquer-franchise-en/game-crashes-when-changing-resolution-cc-34/7214397) describes a resolution-change failure; this reinforces a preview/confirm/revert path instead of saving every displayed value immediately. These community reports are not guarantees about every C&C version or PC.

**UE 5.8 behavior verified against this project's installed source.** `UGameUserSettings` already owns device/display/scalability settings in the `GameUserSettings` config category. `ApplySettings()` applies resolution and non-resolution values and then calls `SaveSettings()`. `ConfirmVideoMode()` and `RevertVideoMode()` explicitly separate display acceptance from reverting. The engine's `Version` property is compared with its own `UE_GAMEUSERSETTINGS_VERSION`; in this UE 5.8 checkout `ValidateSettings()` deletes/reloads the generated config branch when that marker remains invalid. Do not use this engine-owned field as POLITIKA's profile-preference schema version. Preserve the existing `UPolitikaUserSettings::ValidateSettings()` guard, and add any future display-field migrations without silently discarding the entire file. See Epic's [UE 5.8 `UGameUserSettings` API](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/UGameUserSettings?application_version=5.8), [configuration-file hierarchy](https://dev.epicgames.com/documentation/unreal-engine/configuration-files-in-unreal-engine), and [UE 5.8 `ULocalPlayerSaveGame` API](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/ULocalPlayerSaveGame?application_version=5.8), as well as `Engine/Source/Runtime/Engine/Private/GameUserSettings.cpp` and `GameFramework/SaveGame.h` in the pinned checkout. Epic's local-player save class supplies a platform-user association and `GetLatestDataVersion`/`HandlePostLoad` migration hooks; its convenience LoadOrCreate path creates an object when loading fails, so it must not be allowed to overwrite a corrupt or unsupported source before POLITIKA has classified it.

**Serialization and recovery.** Keep defaults in code/typed assets and the two authoritative stores above, not in Rust or a second C# settings service. For the first profile store, serialize the small `ULocalPlayerSaveGame` object and persist it through a profile-specific `SaveDataToSlot` integrity envelope like the existing verified local profile: validate signature, size, and checksum before `LoadGameFromMemory`, then initialize the local-player save object. This protects UE's raw UObject deserializer from arbitrary corrupt bytes. A missing file may create defaults; a malformed or future-version file must remain byte-for-byte intact, surface a recovery status, and run only with temporary defaults until the user repairs or explicitly resets that store. The envelope is accidental-corruption detection, not authentication. Run migrations as sequential, idempotent version steps; write the migrated snapshot only after every step and all current-field validators succeed, and never touch campaign-save slots. The existing synchronous local-profile APIs are suitable only while these snapshots stay small; move to async/atomic-temp persistence before introducing large preference payloads or cloud synchronization.

**Menu and apply behavior.** Add a compact settings screen reachable from the shell menu with **Video**, **Audio** and **Interface** sections, plus separate, labelled restore actions. Bind controls to typed working values and the settings service; do not write config from Slate callbacks or publish unrestricted console variables. For a display preview, stage values, call `SetScreenResolution`/`SetFullscreenMode` and `ApplyResolutionSettings(false)` without saving; show a visible 15-second Keep/Cancel countdown; Keep calls `ConfirmVideoMode()` then persists, while Cancel/timeout calls `RevertVideoMode()` and leaves the previously confirmed mode authoritative. Do not call `ApplySettings()` before Keep, because it automatically saves. Revert if the display disappears or the requested mode fails. Apply user-profile fields through the settings service and save only that store after successful validation; report per-store failures rather than claiming one atomic transaction across both stores. Keep safe mode available throughout a preview.

**Reset boundaries.** Preserve the implemented `-PolitikaResetUserConfig` contract as a device-settings reset only: make an exact dated backup of the generated `GameUserSettings.ini`, reset/reload defaults, and retain local identity, profile preferences and saves. The menu's profile-preferences reset is a separate explicit confirmation and affects only the active preferences slot, retaining the profile ID and campaigns. A future “reset all settings” action must name both stores, create/verify both backups before either reset, and explain partial-failure recovery. Never let UE's built-in engine-version deletion substitute for a user-confirmed reset or a game-owned migration.

**Settings acceptance sequence.**

1. **First-run defaults, validation and failed-write gate.** In two clean isolated user directories, launch the same build with no persisted device/profile settings and compare the resulting typed snapshots against the declared `MakeDefaults()`/UE defaults; values must not depend on launch order, machine-specific display enumeration or a previous run. Use C&C4's separate General/Video/Audio pages as the organization precedent only—the extracted assets establish authored UI, not validation rules. Test each field independently with a valid control and one invalid value, asserting the validator's structured field/reason result, the documented fallback/rejection, and that unrelated fields remain unchanged: every enum outside its declared set; gain and text scale just below/above range plus NaN/infinity where the type permits; an unknown or build-disallowed culture; resolution absent from the current supported-mode list; and a missing/unavailable monitor identifier. Culture lookup should use UE's culture object lookup and build-allowance check ([`FInternationalization` UE 5.8 API](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Core/FInternationalization?application_version=5.8)); do not equate an unknown culture with a known-but-disallowed one. `UKismetSystemLibrary::GetSupportedFullscreenResolutions` enumerates modes but has no monitor argument ([UE 5.8 API](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/UKismetSystemLibrary?application_version=5.8)), so reject/fallback an unavailable monitor through the display/platform adapter rather than pretending this helper validates per-monitor modes. For both authoritative stores, seed known current bytes and inject failures before write, during staged/temp write, and at replacement/commit; after each failure assert the original file hash/bytes are unchanged, no partial candidate is loaded as committed, temporary artifacts are cleaned or clearly recoverable, the prior in-memory values remain active, and a user-visible recovery status plus structured log reason is emitted (never report “saved”). Also cover first-run failure with no prior file: remain on typed defaults and report that persistence failed. Engine field clamping alone is not a substitute for the profile store's explicit typed validators; UE's `UGameUserSettings::ValidateSettings()` may delete a stale settings file ([UE 5.8 API](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/UGameUserSettings?application_version=5.8)), so retain the existing version guard and run the corruption/version fixture without losing the source bytes.
2. **Preferences migration and preservation gate.** Use a unique `-UserDir=` fixture and the same profile ID/slot throughout. Seed a checksum-valid prior-version preference payload with distinctive values for every field; launch once and assert each explicit migration step's old/new version and output typed values, then verify the current version is committed only after migration and current-field validation succeed. Relaunch the same fixture: assert zero additional migration steps, identical typed values, and no duplicate/clamped-again effects. Treat “exactly once” as one durable commit/effect: inject a migration-write failure and restart to prove the old source remains intact and the idempotent migration can safely replay without losing or double-applying values. Independently seed truncated bytes, a checksum mismatch, a checksum-valid future `SavedDataVersion`, and an unknown envelope/schema; hash each source before launch, classify it before any migration/reset path, use in-memory temporary defaults with a visible/logged recovery reason, cleanly exit, and prove the source hash and bytes are unchanged. Do not call `ULocalPlayerSaveGame::LoadOrCreate…` on unclassified data: in UE 5.8 its source creates a new default object when loading fails and calls `InitializeSaveGame()`/`HandlePostLoad()` for a loaded object. Use the known-compatible raw-load/integrity path to inspect the saved data version before invoking migration hooks; if it is future or unsupported, preserve and quarantine it rather than rewriting it. Confirm none of these preference cases reads, migrates, backs up over, or modifies campaign-save slots. C&C4's documented profile-scoped `Options.ini` distinct from saved-game storage is the useful ownership precedent; it provides no migration semantics to copy.
3. **Per-profile save, restart and runtime-application gate.** In one isolated `-UserDir=` fixture, seed two distinct stable local-profile IDs A/B and derive separate preference slots from each profile ID (the identity object remains identity-only). Through the settings UI, set A's music/effects/voice gains, UI/text scale, subtitle choice and high-contrast option to distinctive non-default values; assert the settings service commits a validated typed snapshot to A's slot and reports save completion before clean shutdown. Relaunch A and assert its same profile ID resolves the same slot, every typed value loads before the settings screen/gameplay UI is built, and the settings are applied—not merely displayed: play deterministic test cues routed through each corresponding audio category and measure/inspect the resulting runtime gain (UE 5.8 [Audio Modulation Control Bus/Mix workflow](https://dev.epicgames.com/documentation/unreal-engine/audio-modulation-quick-start-guide?application_version=5.8) is a viable implementation candidate, but is not enabled in the current project); render a fixed menu/subtitle fixture and assert text-scale/layout metrics and subtitle/high-contrast behavior change as specified. Distinguish the user text-size preference from the project's resolution-driven UMG DPI curve ([UE 5.8 DPI scaling](https://dev.epicgames.com/documentation/unreal-engine/dpi-scaling-in-unreal-engine?application_version=5.8)); test at fixed viewport dimensions so DPI changes do not masquerade as profile preference effects. Then launch B in the same user directory: its clean profile must receive typed defaults, not A's values; give B a different value set, save/restart B, and switch back to A to prove both profiles retain their own values and neither shares a mutable singleton/cache. C&C4's extracted [Audio settings page](</mnt/data/CommandAndConquer/UM/Command and Conquer 4 Tiberian Twilight/extracted/Apt/data/aptui/shell_screen_settings_audiopage.manifest>) and PCGamingWiki's [profile-scoped `Options.ini` entry](https://www.pcgamingwiki.com/wiki/Command_%26_Conquer_4%3A_Tiberian_Twilight) provide the UI/ownership precedent; neither establishes audio routing or runtime application semantics for POLITIKA.
4. **Real-window display preview, rollback and override gate.** Run the packaged client in a visible real window (not `-nullrhi`/headless) under an isolated `-UserDir=`. Record the confirmed tuple—resolution, window mode, stable display ID/index—and exact generated device-settings bytes. Select a different mode present in the live supported-mode list, preview it via the no-save apply path, and verify the actual window/viewport dimensions and mode change while the saved tuple/bytes remain unchanged during the 15-second countdown. For Keep, call `ConfirmVideoMode()`, persist once, cleanly exit and relaunch without overrides; assert the actual window and loaded settings match the accepted tuple. For Cancel and forced timeout, call `RevertVideoMode()` and explicitly reapply the restored resolution/window/display tuple without saving; UE 5.8 source shows `RevertVideoMode()` only restores the confirmed setting fields and broadcasts `OnGameUserSettingsVideoRevert`—it does not itself request a platform window change ([`UGameUserSettings` UE 5.8 API](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/UGameUserSettings?application_version=5.8), `GameUserSettings.cpp` in the pinned source). Assert the visible window returns to the previously confirmed tuple and the config bytes remain exactly unchanged. Separately request an unsupported resolution and an unavailable display ID during preview; verify each is rejected or moved to the documented safe fallback, the old confirmed mode remains authoritative, no invalid proposal is written, and display-loss during the countdown follows the same rollback path. Finally seed a saved mode, launch with engine overrides such as `-ResX=1280 -ResY=720 -Windowed`, and assert the live startup window follows the command line while the saved confirmed settings bytes/tuple remain unchanged; relaunch without flags and verify the persisted mode is restored. `UGameUserSettings::ApplySettings()` saves, so use the explicit no-save preview path and distinguish startup overrides from user-confirmed settings. Keep physical multi-monitor/hot-unplug qualification separate from deterministic unsupported-ID fixtures. The C&C4 resolution-change crash report cited above is a secondary failure precedent for verifying the actual revert path, not a platform guarantee.
5. **Scoped reset and shutdown-isolation gate.** In separate fresh `-UserDir=` fixtures, seed each store with a different recognizable byte pattern/value set: device `GameUserSettings.ini`, active-profile preferences, a second-profile preference slot, local-profile identity, and a campaign-save sentinel in its reserved slot/path. For device reset, use its explicit confirmation/launch path; require exactly one dated/unique backup whose bytes equal the original device config, and verify the user-layer device file is removed/reloaded to shipped defaults without changing either preferences slot, local identity, or campaign sentinel. For profile reset, confirm the active profile ID, reset only that profile's preference slot to defaults (or the documented missing-slot/default representation), and verify the other profile's preferences, device config bytes, local identity bytes/ID, and campaign sentinel are unchanged. In both runs, inspect reset outcome/recovery logs, exit orderly, then rehash/re-read every fixture: no stale in-memory setting may be written back during shutdown and no unrelated store may be created, deleted, or rewritten. Relaunch normally and prove the device/profile reset takes effect while the preserved profile/campaign sentinels remain byte-identical. Inject backup/commit failure in each applicable reset path and verify no source is deleted or partially reset and recovery is reported. C&C4's [profile-scoped `Options.ini` versus separate saved-game location](https://www.pcgamingwiki.com/wiki/Command_%26_Conquer_4%3A_Tiberian_Twilight) is an ownership precedent only; the sentinel checks verify that boundary, not successful campaign parsing/loading.
6. **Packaged settings UI and recovery matrix.** Run the cooked packaged client—not PIE or `-nullrhi`—with a fresh isolated `-UserDir=` per case at rendered 3840×2160, 1920×1080, and at least one platform-advertised windowed or ultrawide mode (record the actual viewport size/aspect; if unavailable, report the gap rather than silently skipping it). At each size, capture the Video/Audio/Interface settings screen, a long-text or localized label, the display Keep/Cancel countdown, and a recovery state (corrupt/unsupported preferences or failed settings write); review approved screenshot baselines and assert after layout/paint settles that every actionable widget/focus rectangle is inside the viewport/safe area, text wraps without overlap/clipping, and countdown text/actions remain visible and readable. Repeat after live resize, accepted display-mode change and rollback; confirm the settings panel reflows and focus remains on a valid control rather than jumping behind the modal. Drive keyboard navigation (Tab/arrows, Enter, Escape) and an automated/virtual gamepad path (D-pad/left stick, accept, back) through every settings section, Keep/Cancel and recovery action; assert semantic focus/activation and that modal interaction does not activate hidden controls. Use UE's [DPI scaling](https://dev.epicgames.com/documentation/en-us/unreal-engine/dpi-scaling-in-unreal-engine), [UMG anchors](https://dev.epicgames.com/documentation/en-us/unreal-engine/umg-anchors-in-unreal-engine-ui) and [Screenshot Comparison Tool / Functional UI Screenshot Test](https://dev.epicgames.com/documentation/en-us/unreal-engine/screenshot-comparison-tool-in-unreal-engine) as the responsive-layout and visual-regression references. The editor screenshot tool is methodology/baseline support, not evidence of packaged behavior: capture and review the actual packaged client separately. C&C4's General/Video/Audio pages inform settings grouping, while POLITIKA's 3840×2160 desktop target is an extension beyond that game's display support. Store screenshots, viewport/DPI metadata, per-case logs and input assertions with the package's acceptance record. Keep physical monitor/driver/window-manager, OS display scaling, ultrawide hardware and named controller/platform certification as a separate qualification gate; a virtual gamepad or Xvfb run proves package/UI behavior only, not those devices.

Rust/Cargo may launch these fixtures, parse structured UE log events, compare file hashes and emit bounded diagnostics; C++ remains the single runtime validator/serializer and UE owns display config. The normal Unreal Target/Build C# files remain build rules only. Add no C# runtime, custom INI parser, or Rust mirror of settings policy. Keep game `version.json` compatibility counters independent from both the UE engine `Version` marker and the local-player preferences migration version; increment a compatibility counter only when its documented serialized contract genuinely changes incompatibly.

#### Input contract implementation notes

**Reference findings and transfer.** The [official C&C4 PC manual](https://shared.fastly.steamstatic.com/store_item_assets/steam/apps/47700/manuals/CC4TTpcMANeUS.pdf) groups selection, unit orders, control groups and camera functions into a substantial shortcut vocabulary: for example, Ctrl+0–9 assigns a group, 0–9 recalls it, Alt+0–9 centers the camera, and attack-move/stop have dedicated commands. C&C4's extracted [control-group button](</mnt/data/CommandAndConquer/UM/Command and Conquer 4 Tiberian Twilight/extracted/Apt/data/aptui/tacticalcontrolgroupbutton.manifest>) and [control-groups bar](</mnt/data/CommandAndConquer/UM/Command and Conquer 4 Tiberian Twilight/extracted/Apt/data/aptui/tacticalhudcontrolgroupsbar.relo>) provide shipped UI-asset evidence that groups are presented in the tactical HUD, not proof of live behavior in this environment. Reuse the discoverability principles—named commands, quick selection/recall and clear hotkey hints—not C&C4's fixed key assignments or its unit model. Bind POLITIKA's own typed player intents, keep contextual mouse orders consistent with buttons/hotkeys, and allow preferences to vary by device.

**UE 5.8 starting point and current project gap.** The project currently has no Enhanced Input assets/module dependency or CommonUI plugin enabled; `Politika.uproject` disables engine plugins by default. The shell controller is Slate-only and currently uses `FInputModeUIOnly`; `DefaultInput.ini` sets no mouse capture on launch. Epic's [Enhanced Input overview](https://dev.epicgames.com/documentation/unreal-engine/enhanced-input-in-unreal-engine), [`UEnhancedInputUserSettings`](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Plugins/EnhancedInput/UEnhancedInputUserSettings), [`RegisterInputMappingContext`](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Plugins/EnhancedInput/UEnhancedInputUserSettings/RegisterInputMappingContext), and [CommonUI integration guidance](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-commonui-with-enhanced-input-in-unreal-engine) describe the relevant UE concepts. **Overlay routing is explicit policy.** Treat each interaction as one of: (a) modal shell/settings/pause/recovery/rebinding UI, which suspends or removes gameplay IMCs, activates UI/modal input, captures focus, and prevents underlying world click/order actions; (b) non-modal HUD, where gameplay may remain active but HUD actions are separately scoped and cannot also emit a game command; or (c) a deliberate in-world targeting/command mode, which activates only the relevant target actions and has visible Confirm/Cancel state. ### Resource conversion and faction-specific nuclear permissions

**Ordinary purchasing currency and upkeep:** POLITIKA uses in-game **US dollars ($)** for troop/structure procurement, food supplies and ordinary approved services. Authorized gold or fossil-fuel inventory may be sold for USD while retained commodity stocks continue to support refining and warfare. Buildings have positive minimum electricity demand; deployed staffed forces have per-step food upkeep purchased with dollars. A missing power feed disables normal powered building functions, and empty food reserves produce a recoverable, visible shortage—not a secret immediate force wipe. Exact amounts, shortage effects, sale rates and generators require authored fixtures. See [currency/exchange and upkeep contract](RTS_OPERATIONAL_ECONOMY_AND_POWER.md). Existing tactical prototype lacks these systems.

The game has two required resource-conversion chains. Crude oil from oil fields must be refined in refinery facilities into petroleum fuel or kerosene, with the Atlantic Concord paying a lower refining cost. Natural gas is a separate fossil-fuel source. Crude nuclear materials (the highest-valued resources) must be converted into processed nuclear-material game resources before supporting nuclear plants or weapons. Fossil fuels are second by value; electricity and other resources matter as infrastructure constraints.

The Atlantic Concord and Red Directorate are the only starting nuclear powers and may refine nuclear materials to construct nuclear power plants or their rare, very-long-build tactical weapons. Concord deploys bombs by nuclear bomber, Directorate by ICBM. The Meridian Pact cannot refine nuclear materials at all, has no nuclear construction tree, but can seize completed weapons. It must always start near a valid oil or gas field. The Iron Ascendancy starts without nuclear capability, and its spies must infiltrate a Concord or Directorate nuclear research facility to obtain both nuclear-refining technology intelligence and weapons-production intelligence; only then may it refine for its own first bomb and it cannot construct nuclear power plants. Completion of its first own bomb triggers immediate active-match victory without deployment, whereas theft does not.

Implement these as authoritative, data-driven rules: validated production recipes and costs; input/output inventories; permission and intelligence checks; immutable construction provenance; interruptible refinery/production queues; electricity generation/consumption; map-generation spawn constraints; and a match-level completion-to-victory event. Protect against refinery bypass, double spending, illegal construction permissions and completion through stolen inventory. Exact quantities and timing remain balance work, not real-world technical specifications.

Other asymmetric rules: the Atlantic Concord and Red Directorate have different specialist espionage features, and the Iron Ascendancy alone has Intimidation to convert isolated enemy units. Red Directorate infantry is much cheaper to produce than other factions' infantry; Iron Ascendancy has a modest destructive-power advantage and some high-risk sacrificial attack behavior; Concord refining is modestly cheaper; Meridian starts near fossil-fuel fields. Balance this alongside standard faction doctrine and the Unaligned's neutral sovereignty AI.

See [Resource Economy](RESOURCE_ECONOMY.md) and [Nuclear Ultimate Weapons System](NUCLEAR_WEAPONS_SYSTEM.md). The 1984–1989 Tito conspiracy remains the primary authored story, independent of individual match victory results.

### Espionage progression and Intimidation as gameplay systems

Espionage specializations: Atlantic Concord Psy-Ops can cause a successful full Discipline/Morale breakdown and in-game self-destruction, or instead impose a short, timed friendly-fire rampage without changing ownership; it acts on eligible combat and non-combat units through the single `UnitResolve` state. Red Directorate basic infiltration for rival intelligence theft completes slightly faster and at slightly lower cost than an otherwise equivalent authorized operation. The Iron Ascendancy still has more limited spying, with an explicit upgrade tree whose full completion gates access to Concord/Directorate nuclear research facilities and the associated stolen refining/weapon intel flags.

Intimidation: an Iron Ascendancy-exclusive command/ability may convert eligible isolated combat and non-combat units, but only after fully breaking the shared unit resolve meter (labeled Discipline for combat targets and Morale for civilian targets). Validate category, meter, eligibility and isolation before control transfer. Allied reinforcement and interruption are possible counterplay. No other faction can use Intimidation, and conversion does not replace nuclear research infiltration.

Represent spy progression, facility ownership, unlocked infiltration actions, intelligence provenance, isolation conditions and unit controller transfers as authoritative state, not user-interface assumptions. Add separate test cases for partial versus complete Ascendancy spy upgrades, valid versus invalid research facilities, supported versus isolated intimidation targets, and unit ownership/persistence after a successful conversion. See [Espionage and Intimidation](ESPIONAGE_AND_INTIMIDATION.md).

### Psy-Ops and reduced intelligence-theft costs

Psy-Ops and intelligence theft should be simulation-owned game actions rather than scripted UI effects. Validate Concord-only permission, target category/eligibility, authorized application of `UnitResolve` loss and a full-break event before Psy-Ops self-destruction. The rampage path uses a temporary, expiring friendly-target override that does not permanently alter owner, faction or diplomacy. The enemy unit must have a valid in-game attack capability. Directorate intelligence theft applies modest, data-driven reductions to cost and duration only for qualifying intelligence-acquisition operations; all research-site infiltration requirements remain unchanged. Unit ownership changes belong solely to separately authorized mechanisms such as Ascendancy Intimidation.

### Building infiltration, resource diversion and staffed-facility disruption

Represent special facility espionage actions as authoritative RTS state transitions with their own eligibility, resolution, visibility and recovery. These are separate from unit `UnitResolve`.

- Atlantic Concord building Psy-Ops: after authorized infiltration, either trigger an eligible building's destruction or apply a capped covert resource-waste status, debiting the victim without crediting the Concord.
- Red Directorate budget diversion: atomically debit a valid enemy budget/inventory and credit a compatible amount to the Directorate budget. Respect availability, item type, storage limits, transaction idempotency and protection against duplicate credit; the opponent may initially lack attribution.
- Iron Ascendancy contamination: use an abstract facility-level poison/disease disruption state to cause simulated deaths in assigned workers/researchers. Calculate reduced staffing, impaired throughput, complete stoppage below staffing requirements, and a finite propagation chain among nearby eligible facilities. Containment, staffing replacement, clearing the status and repair are gameplay recovery conditions.

Maintain `FacilitySpyAction`, `IncidentVisibility`, `IncidentAttribution`, `CovertBudgetTransfer`, `ResourceWaste`, `FacilityWorkforce`, `StaffLossEvent`, `FacilityThroughputModifier`, `FacilityContaminationState`, `AffectedNeighborIds`, `SpreadDepthCap`, `AffectedFacilityCap` and `ContainmentResult` or equivalent data-driven components. Do not treat a hidden incident as an invisible change to actual resource amounts: simulation data remains correct while the defending UI may not reveal its cause.

Buildings are not soldiers and do not have a combat Discipline meter. An unattended facility can still have workforce/production state. Nuclear research acquisition, first-bomb victory and player-faction ownership remain gated by their existing separate authoritative checks. These poison/disease effects are purely fictional facility statuses with no modeled real-world chemical or biological process. See [Espionage and Intimidation](ESPIONAGE_AND_INTIMIDATION.md) and [Resource Economy](RESOURCE_ECONOMY.md).

### Reconnaissance units and faction-access restrictions for explosive sabotage

Create data-driven early scouting archetypes for the four playable factions: cheap, very fast, lightly armored/armed half-scout/half-combat trucks for Meridian Pact (the best overall reconnaissance faction); cheap, unarmed light scouting airplanes for Atlantic Concord and Iron Ascendancy; and rifle-armed motorcycle scouts for Red Directorate. Ordinary visibility, unit production, vehicle movement, air movement, target detection and combat abilities govern these units. Reconnaissance never grants a classified intelligence unlock, even after revealing a nuclear research facility.

A separate conventional explosive-sabotage ability acts on eligible enemy vehicles and buildings through a fictional charge-placement game interaction and conventional damage event. Faction permission rules are strict: Meridian can use it cheaply and early through designated non-spy units; Concord, Directorate and Ascendancy can only unlock it later, at greater cost, and execute it with spy units alone. Scout identity is not an automatic sabotage permission: authorize Meridian truck archetypes explicitly if intended, and reject non-spy rival scouts regardless of target visibility.

Suggested properties: `ReconUnitType`, `MovementLayer`, `MovementSpeed`, `SightRange`, `CanAttack`, `ScoutCombatRole`, `SabotageTechUnlocked`, `SabotageCost`, `ExplosiveSabotageActorEligible`, `TargetKind`, `ChargeStatus`, `ExplosionEvent`, `SabotageAttribution` and `DefenderCountermeasure`. Never mix this sabotage charge with nuclear weapons or with the faction-exclusive Psy-Ops, intelligence theft, contamination and Intimidation systems. The simulator, not the UI, enforces early/late availability, spy-only rivals, conventional damage and target eligibility. See [Reconnaissance and Scouting](RECONNAISSANCE_AND_SCOUTING.md) and [Explosive Sabotage](SABOTAGE_SYSTEM.md).

### Shared unit resolve: combat Discipline and civilian Morale

One unit meter, two UI names. Each combat or civilian/non-combat unit owns one authoritative `UnitResolve` value, with the same depletion, recovery and broken threshold mechanics. Combatants display “Discipline”; civilians/non-combat units display “Morale.” Do not instantiate separate discipline and morale component classes for individual units. Every faction additionally exposes Population Morale, a faction-level summary of the shared morale framework informing production and soldiers' baseline Discipline.

Formation benefits apply to combat Discipline only. Red Directorate, Iron Ascendancy, Meridian Pact and Unaligned units receive standard coherence/size bonuses; the Red Directorate and Iron Ascendancy additionally gain an extra bonus for very massive coherent armies. Atlantic Concord soldiers incur no solo/very-small-group Discipline penalty. Civilians' Morale does not receive mass-army Discipline modifiers.

Intimidation targets both kinds of eligible isolated unit: the Iron Ascendancy must first fully break Discipline for a combat target or Morale for a civilian/non-combat target before converting it. Both use the same `UnitResolve <= BrokenThreshold` check; eligibility, isolation, meter loss and ownership transfer must be validated in order. The conversion of one civilian does not zero faction Population Morale or create another player faction.

Tests: identical numeric threshold/recovery for both categories; proper labels; no conversion before the meter is broken; no conversion without isolation; no mass-army perk for civilians, Meridian or Unaligned; solo Concord combat immunity to formation-size penalty but not direct coercion. See [Propaganda and Morale](PROPAGANDA_AND_MORALE.md) and [Espionage and Intimidation](ESPIONAGE_AND_INTIMIDATION.md).

### Military formations, stances and cohesion — core unit-behavior extension (proposed)

[Military Formations, Tactical Stances, Cohesion and Discipline](RTS_UNIT_FORMATIONS_AND_DISCIPLINE.md) owns persistent tactical formations, shape/role assignment, independent combat stances and adherence, spatial Cohesion, and their effects on the **existing single per-combatant `UnitResolve`** Discipline. Local selection/control groups confer neither membership nor bonus. Each member continues using ordinary typed command admission and fixed-step legal movement; do not introduce independent Actor-Tick formation navigation or local Unaligned player control. Line/Column is the first bounded shape slice; Dispersed/Perimeter and advanced geometries follow.

**Delivery order:** relevant NAV lifecycle/failure/scale proof, 4C independently validated multi-issuer group orders, then FORM-F2 eight-unit shape movement, FORM-F3 persistent organization, and separate FORM-F4–F8 stance/cohesion/advanced integration tests. Military formations are intended as a core mechanic but **not implemented** and not a new prerequisite to declare the ordinary Stage 4F skirmish accepted. Existing NAV/GRP/4F evidence is not promoted by this design.


### Advanced propaganda and faction morale

Provide an authoritative per-faction morale state for all five factions, including the NPC Unaligned and non-propaganda Meridian Pact. High morale boosts eligible production throughput and army discipline by data-driven, capped modifiers. Propaganda actions are available only to Atlantic Concord, Red Directorate, Iron Ascendancy and Unaligned, with different faction-specific methods expressed through radio, newspapers and television. Meridian Pact has no advanced propaganda ability tree.

Media facilities have controllable faction/jurisdiction, functioning/power state, distribution or broadcast reach, counteraction and objective events. The match/simulation layer owns morale and outcomes; AI selects and applies Unaligned media actions; content assets define faction eligibility, audience, cost, duration and modifiers; UI displays morale and accessible actions. Avoid implementing morale as a visual-only bar. See [Propaganda and Morale](PROPAGANDA_AND_MORALE.md).

### Unaligned AI intelligence director and dynamic equilibrium

Add a distinct Unaligned NPC counterintelligence and false-information director to the match/simulation architecture. The Unaligned has the strongest such capability: it can intercept actual rival intelligence according to intelligence-coverage rules, fabricate claims or false-flag attributions, and disseminate them as plausible reports to specific active players. Claims may concern a nuclear research facility that does not exist. Never mutate true facility, nuclear intelligence, unit, resource, ownership or victory state merely to make a false report convincing.

Keep authoritative ground truth separate from the recipient-specific intelligence layer: `IntelClaim`, `ClaimSource`, `RecipientFaction`, `Confidence`, `VerificationState`, `FalseIntelOperation`, `AttributionState`, `ClaimExpiry` and `ReportedLocation`. An actual scout observation can contradict a forged marker. NPC interception and disinformation have eligibility, cooldown, cost and discovery limitations rather than omniscient automatic visibility.

The Unaligned balance director can evaluate faction strength—surviving troops, resources, production assets and imminent elimination risk—across the actual 2–4 participants. When one faction is very weak and faces imminent destruction, it may plant misinformation designed to redirect stronger rivals' attention to one another. This is a bounded AI choice, not a scripted veto of player victory, forced retargeting or free grant of resources. The Unaligned's exceptional hostility toward identified Ascendancy forces persists. Verify that no false nuclear research report can satisfy the Ascendancy's verified real-facility spy gates or delay an earned own-first-bomb match win.

See [Unaligned Counterintelligence](UNALIGNED_COUNTERINTELLIGENCE.md), [Match Structure](MATCH_STRUCTURE.md) and [Espionage and Intimidation](ESPIONAGE_AND_INTIMIDATION.md).

### Match-size and player-to-faction invariant

Ordinary matches have exactly 2, 3 or 4 occupied playable faction slots, drawn from Concord, Directorate, Ascendancy and Meridian, plus one always-present Unaligned NPC/system-AI faction. Each player or AI-opponent controller is assigned exactly one distinct playable faction; Unaligned has its own autonomous system controller and does not consume a player slot. The local single-player case may therefore be one human and one or more AI-controlled playable opponents.

The match framework validates unique faction selection, player/faction mappings and capacity (2–4), and spawns Unaligned separately. World/content validation ensures correct spawn counts and Meridian's nearby fossil field. The UI must distinguish player slots from faction presences and never show the Unaligned as a selectable player. An Ascendancy nuclear-infiltration victory requires a qualifying opposing Concord or Directorate research facility when enabled; the framework must not manufacture one from the Unaligned just to satisfy the rule. See [Match Structure](MATCH_STRUCTURE.md).

## 4. Content model and authoring

Represent each faction, unit, weapon, ability, upgrade, objective type and AI personality as versioned data assets with stable IDs. Definitions should reference reusable gameplay components/abilities, not hide behavior in arbitrary per-unit blueprints. Blueprint subclasses are appropriate for presentation and authored special cases; shared simulation rules belong in tested C++ systems.

Keep content definitions inspectable and data-oriented. Unit and vehicle archetypes should explicitly describe owning faction, available commands, armor, speed, weapons, health, collision geometry, vision, and reusable behavior modules. Keep map data, skirmish AI, mission parameters, progression, audio and interface definitions in validated, versioned UE-native assets or clearly specified schemas. This enables designers to review and balance content without reverse-engineering the gameplay code.

Maps need authored playable bounds, terrain/navigation representation, spawn/deployment points, control/resource objectives, blockers, scripted regions, camera bounds, lighting/audio setup, and validation rules. Build a map validation pass early (missing spawns, unreachable objectives, invalid references, camera bounds, faction-specific constraints).

### Map authoring contract and validation pass

Represent a playable map as a UE-authored level plus a small, versioned map-definition asset that names its stable map ID, validation profile (test/skirmish/campaign), playable/camera bounds, supported match sizes, faction/spawn slots, deployment zones, objective/resource markers, and any declared scripted exceptions. Keep visual terrain and authored placement in the level; keep match-critical identities and constraints explicit and inspectable. Do not infer spawn/resource identity from actor names or editor ordering. Use one validator implementation from editor validation and CI, with a packaged pre-match check for hard invariants; emit diagnostics with map ID, actor/marker ID, and failed rule. Separate **errors** that make a map illegal/unplayable from **warnings** about balance/readability so intentional campaign setups can be expressed through explicit profiles rather than hidden exceptions.

- **Structural checks:** map ID/version is valid and unique; bounds are positive and contain all required playable actors/markers; camera bounds intersect playable bounds; all referenced faction, objective, resource, and spawn definitions resolve; marker IDs are unique; configured match sizes have the required number of legal slots; no required start or deployment area is missing. Validate only the chosen map profile's requirements (e.g. campaign-only scripted starts need not satisfy a skirmish roster).
- **Spatial/gameplay checks:** every spawn point and deployment zone lies on legal passable terrain and does not overlap forbidden blockers or another exclusive spawn; each enabled movement class has a route from every required start to its declared initial objectives and usable strategic resources; objective/control regions are reachable and do not sit outside playable bounds; resource markers are legal, non-overlapping and satisfy the selected ruleset's required resource availability. Check buildable/placement areas against the actual POLITIKA building rules where relevant, rather than assuming the reference game's terrain semantics.
- **POLITIKA ruleset checks:** for a standard 2–4 playable-faction match, validate unique faction assignments and enough starts/deployment zones for the selected occupied slots, then place the Unaligned presence/controller according to its own authored rule rather than counting it as a player slot. Enforce Meridian's nearby usable oil or gas field according to the map/ruleset's declared distance and reachability metric. Check enabled Ascendancy infiltration-victory scenarios for at least one qualifying opposing Concord or Directorate research facility only when that win condition/ruleset requires it; never synthesize a facility to make a fixture pass. Validate resource-chain prerequisites and any mission-specific objective dependencies without requiring irrelevant campaign content on skirmish maps.
- **Path/reachability method:** run the validator against POLITIKA's movement-layer navigation/occupancy representation, not just visual proximity or a generic UE NavMesh query. Report the movement class, endpoints and blocked/disconnected result. Cache derived topology only as an editor/CI optimization and invalidate it when terrain, blockers, movement costs or bounds change. Keep expensive balance metrics (travel-time symmetry, objective exposure, choke widths) as warnings/reports initially; promote them to errors only after POLITIKA establishes measurable design thresholds.
- **Tool boundary:** UE C++ Editor validation/commandlet code owns level and gameplay-rule interpretation, since it can load cooked/authored assets and query the same navigation data as the game. A Rust helper may launch validation, collect deterministic JSON/text diagnostics, and enforce CI exit status; it must not parse undocumented `.umap` internals or duplicate reachability/faction logic. The packaged client repeats cheap hard checks before match start and blocks launch with a recovery/error panel rather than entering a broken match.
- **Acceptance fixtures:** a valid test/skirmish/campaign map passes repeatably; negative fixtures independently cover missing/duplicate starts, invalid marker references, a marker outside bounds, blocked/overlapping spawn, unreachable objective/resource for a named movement layer, insufficient match slots, invalid faction assignment, Meridian without a reachable oil/gas field, and an unmet enabled infiltration-victory prerequisite. Each failure identifies the exact map/rule/marker and returns a failing CI result; warnings do not fail unless policy says otherwise. Validate one intentionally exceptional campaign map by declaring its profile/exception and prove this does not weaken skirmish checks. Finally load the valid map in a packaged build and verify required starting entities/objectives resolve before the match begins.

**Reference transfer:** C&C4 WorldBuilder's [README checklist](</mnt/data/SteamLibrary/steamapps/common/Command and Conquer 4 Tiberian Twilight/WorldBuilder README.txt>) calls out player starts, spawn zones, terrain/passability/buildability, objectives/resource nodes, and map sizing/symmetry. Those are useful categories for POLITIKA's validator, while C&C4's team sizes, TCN/crystal names, and tool-specific limits are not POLITIKA rules. The README also says its public tool release is intended for multiplayer/skirmish maps and that custom single-player campaigns are unsupported; use its checklist as a design reference, not as proof of campaign workflow or game behavior. OpenRA's local [processing report](</mnt/data/CommandAndConquer/RA/OPENRA_PROCESSING_REPORT.md>) further confirms map conversion is title/importer-specific, not universal; POLITIKA should validate its own UE level assets and avoid making legacy conversion a runtime dependency.

### Content validation contract and first implementation

Treat authoring data as a versioned contract between designers, UE runtime code, and build validation—not as an informal collection of editable fields. Begin with a deliberately small slice (one faction, one infantry archetype, one vehicle, one weapon, and one map/objective fixture); extend the schema only when a real authored use case requires it.

- **Identity and compatibility:** Every reusable definition has a stable, namespaced `FPrimaryAssetId`/project ID and an explicit schema version. Renaming or removing an ID requires a declared redirect/migration; never derive save- or gameplay-facing identity from an asset filename or display label. Keep display/localization keys separate from IDs. Reject unsupported future schema versions rather than guessing.
- **Types and required values:** Use enums/Gameplay Tags for bounded categories, typed soft references for asset dependencies, and explicit units for quantities (for example seconds, meters, damage points). Mark fields as required or optional; defaults are authored centrally and deterministic. A missing optional presentation field may use a documented fallback, but missing gameplay-critical values must fail validation rather than silently become zero or a plausible-looking default.
- **Validation layers:** Run local field checks (finite numbers, ranges, legal enum/tag values, non-empty required fields), identity/asset checks (unique IDs, resolved references, supported schema versions), and domain checks (weapon/ammo compatibility, faction command permissions, squad composition, objective prerequisites, production recipe inputs/outputs, and cycles where dependency cycles are forbidden). Report the asset ID, property path, and actionable reason. Authoring-time checks may collect multiple errors; runtime loading must refuse invalid authoritative gameplay definitions and surface a recoverable diagnostic instead of partially constructing them.
- **Ownership in UE:** C++ `UPrimaryDataAsset`/Asset Manager types and gameplay enums define the runtime contract. Editor validation should use UE Data Validation and a project validator/commandlet so the same C++ rules gate editor submissions and CI; keep widget/Blueprint presentation from becoming an alternate source of gameplay defaults. Validate hard invariants at load/match setup too, since packaged builds cannot rely on editor validation having run.
- **Tooling boundary:** Rust may lint project-owned source manifests, generated reports, ID registries, or other stable text inputs in CI, and can invoke UE commandlets. It must not implement a competing runtime schema, reverse-engineer UAsset serialization, or claim success without the UE validator. C# is optional for external pipeline integrations only; no runtime dependency is introduced for this contract.
- **Acceptance starter:** A clean fixture validates with stable IDs and defaults across repeated runs. Fixtures with a duplicate ID, missing required value/reference, unknown enum/tag, out-of-range/non-finite number, incompatible version, forbidden dependency cycle, or invalid faction/objective relationship each fail with the exact asset/property diagnostic and non-zero CI result. An unused optional presentation field gets its documented fallback. A packaged match refuses an invalid gameplay definition before play begins, while valid definitions load identically in editor and package.

**Reference transfer:** The archived [C&C mod-support pack](</mnt/data/CommandAndConquer/CnC_Modding_Support/README.md>) includes typed XML schemas and examples that illustrate explicit composition/required-module constraints; it is useful to study schema organization and validation cases, not to import its XML format or EA game rules. The repository’s [license](</mnt/data/CommandAndConquer/CnC_Modding_Support/LICENSE.md>) is GPLv3 with additional EA terms, so keep its files as a reference corpus and do not copy schemas, examples, or assets into POLITIKA without a separate provenance/licensing review. POLITIKA’s contract should remain owned C++/UE data assets with UE validation as the runtime/build authority.

Generate any package inventory from the UE Asset Registry/loaded assets instead of hand-maintaining a second copy of IDs and references.

## 5. 4K as a first-class target

Treat 3840×2160 as a **desktop high-resolution target**, not a universal minimum or a requirement for Steam Deck/Android devices. Support adaptive resolutions, screen sizes, input methods, scalability tiers and safe areas across the declared platform scope.

- Display: windowed, borderless, and fullscreen modes; correct 16:9 aspect; runtime resolution changes; DPI-aware UI scale; safe margins; configurable text/UI scale.
- UI: design in logical layout units, anchor responsively, and test HUD, menus, tactical map, tooltips, text, selection rings and cursor at 1080p, 1440p, ultrawide, and 4K. At 4K, preserve readable world scale without making the command surface tiny.
- Rendering: configure UE scalability and screen-percentage/upscaling options; validate temporal upscaling, anti-aliasing, shadow quality, and post-processing at 4K. Expose quality presets instead of assuming all hardware renders native 4K at max settings.
- Assets: provide appropriate source resolution/mips for UI, terrain, decals and faction insignia; use texture streaming and memory budgets so 4K does not require every asset resident at maximum mip.
- Camera/input: ensure selection, placement and cursor precision work across DPI scaling and display changes; keep world-space camera behavior independent from HUD scaling.
- Acceptance target: no clipped/overlapping controls, text legible at normal viewing distance, correct aspect/camera bounds, and stable input after resolution/DPI changes on a 4K display.

4K support is not equivalent to a 4K render target alone: UI scaling, asset sharpness, memory/performance, and usability must all pass.

## 6. Performance, determinism, and networking posture

Set target player count, entity counts, map size, minimum hardware, and frame-rate target before selecting detailed simulation strategies. Avoid one heavyweight Actor/Tick per small gameplay concern: batch perception, timers, movement updates and UI notifications; profile representative combat scenes early. UE Mass can be evaluated for very high entity counts, but should not be adopted without a prototype demonstrating a concrete benefit.

Keep simulation state and commands explicit and serializable. **Multiplayer is required as an immediate development priority**: use server-authoritative rules and replicate commands/state/events rather than trusting clients; design bandwidth and late-join/reconnect behavior deliberately. If deterministic replay or lockstep is required, validate floating-point and physics assumptions in a prototype first—UE's general simulation should not be presumed deterministic across machines. A replay can instead record timestamped player commands plus synchronized state checkpoints if that meets the product goal.

### 7.1 Cross-stage engineering and promotion rules

1. **Keep one authoritative implementation.** UE 5.8.3/C++ owns match rules, content interpretation, runtime spatial legality and validation of gameplay assets. Rust orchestrates local quality checks, validates project-owned text/report schemas and can invoke UE commandlets; it must not become a second gameplay simulator, a second map interpreter, or a parser for undocumented Unreal binary assets. C# is optional for justified external tools.
2. **Extend proven functionality without quietly replacing it.** Every stage has a baseline comparison against the previous accepted fixture, including successful and rejected orders, state changes, objective behavior, shell startup and package launch. Changes to the actual rules require an explicit design decision and newly versioned acceptance expectations, never an accidental content-extraction side effect.
3. **Treat implementation and qualification as different facts.** Classify evidence as design/proposed, source implemented, validated locally, verified in packaged gameplay, and separately platform-qualified. A unit test, editor validation, successful cook, screenshot or process exit is not interchangeable with rendered interactive gameplay on a target device.
4. **Use one set of rule validators in multiple execution contexts.** Shared C++ validation functions should underpin editor messages, scripted validation and pre-match runtime admission. The editor may perform extra slow/authoring checks, but the packaged runtime must recheck hard match-critical invariants without relying on editor-only classes or data. An invalid match must fail *before* units and objectives are partially spawned.
5. **Build the smallest fixture that makes a claim testable.** Prefer a small positive case and focused independently failing cases to large generalized frameworks. Stage 3 does not require all four playable rosters, complete faction economies, resource graphs, sophisticated navigation, campaign triggers or fabricated historical/map metadata.
6. **Promote by evidence, not calendar or feature count.** Capture the Git revision and dirty state, engine pin, content/schema identity, exact command, target/build configuration, test data, expected/observed result, logs, and unresolved exceptions. Use the existing Rust verdicts (PASS, FAIL, BLOCKED, INFRA_ERROR, INCONCLUSIVE, SKIPPED, NOT_RUN) without converting missing test coverage into success. Apply [Validation and Governance](VALIDATION_AND_GOVERNANCE.md), [Performance and Release Gates](PERFORMANCE_AND_RELEASE_GATES.md) and [Versioning and Release Management](VERSIONING_RELEASE_MANAGEMENT_ROADMAP.md).
7. **Protect offline and cross-platform architecture.** New simulation logic must not depend on a platform-specific window, account, input gesture, graphics feature or online service. Desktop pointer controls remain a prototype binding, not the only legal command source. The [Platform Plan](PLATFORM_SUPPORT.md) owns subsequent Linux, Windows, SteamOS/Steam Deck and Android qualifications; all are planned targets, not automatically tested ports.
8. **Avoid premature infrastructure.** Do not add hosted CI workflows, permanent feature branches, generic visual scripting, universal databases, engine-wide abstraction layers, network lockstep or UE MassEntity solely to satisfy a diagram. Reconsider such tools after a measured need and an explicit scope decision.
9. **Use Tempest Rising as a deliberate engineering reference.** Before committing to the design of each substantial RTS engine feature or milestone, check whether the acquired Tempest editor/manual/API, authored-data, asset-registry, or bounded native-code evidence answers a concrete POLITIKA question. This is a comparison step, not a requirement to find or adopt a Tempest analogue for every task.

#### Reference-guided feature workflow

For each relevant feature slice, add a short reference checkpoint to its owning design/acceptance record (do not create a parallel engine roadmap):

1. **Name the POLITIKA gap first.** State the project-owned behavior and current limitation, inspect its existing implementation/owner contract, and frame one or more questions where a mature RTS example could reduce design risk. Typical searches include unit/weapon/ability composition, player slots and starts, movement/navigation data, production recipes and queues, command eligibility/feedback, map/objective authoring, and HUD or editor workflows. Do not search for abstractions without an identified gameplay or tool-chain need.
2. **Inspect the narrowest available Tempest evidence.** Prefer documented Map Editor/manual/API behavior and directly inspected authored-data fields/relationships; use the case-preserving Asset Registry and tag index for discovery, not semantics. Consult REA/Ghidra only for a specific unresolved binary question. Record exact source file and page/line or exact side/class/package path, source-manifest identity where applicable, and evidence class. The client/server EXE analyses are partial/time-limited and cannot establish mechanics; registry co-presence is not a reference; editor documentation describes an authoring contract, not proof of shipping runtime behavior.
3. **Compare against POLITIKA and UE 5.8.3.** Mark each finding `documented`, `data-inspected`, `runtime-observed`, `registry-only`, or `unknown`; separate transferable structure/workflow from source-game rules, balance, platform constraints, and expressive content. Check the current POLITIKA owner document and exact UE 5.8.3 APIs before proposing an implementation. Tempest's editor project/documentation targets an older UE minor, so its types and binary assets are not assumed compatible.
4. **Record a disposition and implementation delta.** For each useful finding record: the POLITIKA question/gap, exact evidence, confidence and limits, disposition (`adopt-concept`, `redefine`, `defer`, or `exclude`), intended POLITIKA owner, what changes in the POLITIKA design/code/fixture, and what is explicitly not transferred. `adopt-concept` means only a general design idea; it never means copying proprietary code, values, identifiers, or rules. If the evidence provides no useful answer, say so briefly and continue from POLITIKA's own contract.
5. **Implement and accept the POLITIKA version.** Keep authoritative simulation and gameplay policy in project-owned C++ and authoring defaults in UE 5.8.3 assets/config. Add only the smallest necessary schema/runtime extension, then derive positive, negative, failure/recovery, and packaged checks from POLITIKA's own acceptance contract. Preserve versioning, naming, stable-ID, lifecycle, authority, and performance owners. Reference findings inform a proposal; only the existing project decision/acceptance process can change a rule or milestone boundary.

Use the existing case-safe offline index and category/relationship crosswalk under `/mnt/data/CommandAndConquer/UM/Tempest/politika-transfer/`; its draft remains research metadata until the project owner reviews it. The supporting utilization analysis and full extraction/REA report are under `/mnt/data/CommandAndConquer/REA/Tempest/`. Keep generated indexes/crosswalks and extracted data outside the POLITIKA repository and cooked content. Refresh their input hashes and rerun the validator if the source inventory changes. Detailed source-vs-destination naming and evidence rules are in the local-only [Tempest utilization roadmap](/mnt/data/politika/Docs/LOCAL_TEMPEST_UTILIZATION_ROADMAP.md).

**Selective import boundary:** make the initial reuse substantial in research metadata, authoring relationships, validation ideas, and POLITIKA-owned implementations—not in recognizable game content. Do not import Tempest executables, Blueprints, gameplay values, maps, faction identity, UI, signature effects, or recognizable audio. Avoid importing 3D assets by default; a rare generic candidate may be considered only after item-level provenance/rights and dependency review, UE 5.8.3 import/cook proof, project naming/renaming, and a POLITIKA art-direction/recognizability review. Prefer original or commissioned art and use Tempest only as an internal reference. Any audio candidate must additionally be converted to a POLITIKA-named `.mp3`, with source/output hashes and conversion settings recorded; renaming or conversion alone does not clear any gate. Rejected or uncleared candidates remain quarantined outside the project.

**Shared stage gate:** *(a)* the stage-specific positive and negative tests pass, *(b)* the previously accepted shell and gameplay fixtures remain operable, *(c)* diagnostics are reproducible and distinguish content defects from missing tooling, *(d)* a real cooked/packaged path is exercised when the stage promises packaged behavior, and *(e)* remaining non-goals and unqualified platforms are recorded. Passing the shared gate does not imply a release candidate.

### 7.6 Stage 5 — missions, opposing AI and the Unaligned's specialized role

**AI expansion authority:** [RTS AI Architecture](RTS_AI_ARCHITECTURE.md) owns the layered decision vocabulary and proposed later AI-X acceptance; [Opponent AI](RTS_OPPONENT_AI.md) remains the first 4D gate. 5C introduces bounded operational and strategic improvements after the normal skirmish; 5D introduces institutional Unaligned patrol/protection; 5E adds information claims and deception once observation and relevant faction rules qualify. No extra simulation authority, global AI omniscience or new player faction is permitted.

**Dependency:** the match loop supplies authoritative events, stable mission references, observable participant views, command admission and complete results. A mission script or AI policy must not directly teleport ownership, health or resources around the established rules without an explicit privileged, logged scenario action.

**Ordered development:**

1. **5A — objective and mission composition:** create a versioned mission definition referencing validated map/marker/entity IDs; add triggers, timers, conditional branching, optional/mandatory goals, briefing and debriefing content, cutscene/dialogue hooks, checkpoints and failure causes. Keep mission scripts declarative or constrained, with typed actions and event-driven callbacks instead of arbitrary game-state mutation.
2. **5B — one representative alternate-history Yugoslav mission:** build a historically reviewed, original map/mission rooted in the 1984–1989 setting (for example a guarded transport, industrial/communications facility or contested evidence site). Demonstrate a civilian/Unaligned presence, one meaningful strategic decision and a recoverable failure path. Archive evidence and asset rights remain developer-facing; fictional in-world proof/claims follow separate gameplay provenance rules described in the [Yugoslav World Model](YUGOSLAV_WORLD_MODEL.md).
3. **5C — expanded decision-making:** the First Playable Skirmish already requires a bounded deterministic opponent; this increment improves its finite decision set (defend, scout, acquire/deploy, attack/capture, retreat), planning cadence and tactical coordination. Run AI through the same validated order API and participant-specific observation contract as humans; provide logs of *what it knew*, intended command, admission decision and observed result. Do not grant omniscient access through convenience queries.
4. **5D — autonomous Unaligned agency:** implement baseline patrol/protection/escalation and diplomacy before balancing intervention. The Unaligned remains NPC-only and ordinarily neutral, with the game's specified exceptional hostility and legitimacy rules. Its institutions and special inner security layer may differ in knowledge without becoming additional playable factions or automatically sharing the campaign secret. Keep actions auditable by agent/mandate and observable permissions.
5. **5E — espionage, disinformation and asymmetric goals in slices:** implement reconnaissance and real/remembered sightings first; then typed intelligence claims, interceptions, false reports and verifiable provenance. Unaligned fabricated intelligence changes recipient beliefs or decisions **without rewriting world truth**; tests must prove wrong beliefs and the eventual discovery/correction path. Add Meridian contracting/sabotage, faction espionage and later nuclear-victory prerequisites separately when their owning content/rules are authored. Each mechanic should have an adversarial counter-test, disclosure/visibility rule, AI-consumption path and failure feedback.
6. **5F — mission authoring/debugging:** provide event timelines, objective-state inspectors, command-admission traces, agent-knowledge overlays gated to development builds, scenario reset and seeded fixture execution where supported. Keep editor visualization from affecting the authoritative runtime. Expand content validation by actual scenario needs, including dependency cycles, unreachable mission prerequisites and illegitimate scripted ownership.

**Exit gate:** one repeatable campaign mission and one repeatable small skirmish operate in a packaged Development build; AI can carry out and lose a lawful match using only its accessible information; mission branching/objectives work without a UI-owned rule; Unaligned actions preserve NPC-only authority; tests explicitly cover at least one intercepted/fabricated claim once the claim system is in scope. Do not mark *the entire* story campaign, complete factions, all espionage systems or final narrative art complete from this representative mission.

### 7.7 Stage 6 — measured scale, platform adaptation and release readiness

This stage should **integrate performance and product qualification**, not postpone all profiling until the project is large. Start lightweight measurements when Stage 3 content loads; build reproducible cases in Stage 4; instrument fog/AI in Stage 5; perform final optimization and package/device acceptance here. [Performance and Release Gates](PERFORMANCE_AND_RELEASE_GATES.md) owns case identities, metrics and promotion thresholds.

- **6A — reproducible workload suite:** populate the existing planned `small_skirmish`, `group_pathing`, `fog_and_ai` and `render_stress` cases only when each workload actually exists. Record map/content version, random seed where meaningful, entities, match state, camera, quality profile, warm-up, engine/build revision and tested hardware. Track median/p95/p99 frame and simulation time, hitches, command-to-accept delay, path queries, fog/AI cost and peak memory when instruments permit; never advertise hypothetical unit counts as benchmark results.
- **6B — profile before replacing architecture:** use UE [Unreal Insights and performance profiling](https://dev.epicgames.com/documentation/unreal-engine/introduction-to-performance-profiling-and-configuration-in-unreal-engine), in-engine stat traces and platform GPU tools to identify main-thread, render, asset, memory or pathfinding bottlenecks. Consider event batching, spatial partitioning, group path requests, actor pooling, instancing/LOD, simplified effects and conditional UE Mass only after a representative comparison shows benefit without breaking RTS order semantics. Measure worst-case spikes as well as average FPS.
- **6C — input/display portability:** maintain one semantic selection/command API while giving Linux/Windows keyboard-and-mouse **and controller** profiles, SteamOS/Steam Deck gamepad/trackpad profile, and Android touch-first interaction distinct layouts. Check target/cancel operations, selection feedback, pause, accessibility, localization, safe areas and density. Preserve 4K-capable desktop readability and adapt to 1080p/1440p, ultrawide and handheld/mobile screens without assuming handheld 4K rendering.
- **6D — platform-native packaging and playtests:** qualify Linux and Windows builds independently on supported hardware, SteamOS/Steam Deck on actual handheld hardware, and Android on defined devices/API/graphics tiers. - **6E — multiplayer scaling/release hardening, not the start of networking:** MP-0 existing-code audit and MP-1 listen-server proof start **now**, with MP-3 headless parity and incremental MP-2 qualification as soon as prerequisites allow. Stage 6E only revisits later network workload, public sessions, spectator/reconnect, anti-cheat/security, and replay integration. Baseline candidates are timestamped admitted commands and periodic versioned state checkpoints; do not assume deterministic cross-platform lockstep. A replay or online mode needs its own correctness, compatibility, desync, late-join and security test matrix before inclusion.
- **6F — content, rights and release audit:** validate imported map/art/audio dependencies and source permissions; finish target-specific performance and input gates; check localization, accessibility, readable mission UI, crash recovery, release identity, migration/save compatibility, packaging/install behavior and missing asset reports. The archive and production ledgers are part of provenance review, not an automatic grant of publishing rights.

**Exit gate:** a named release candidate passes the [platform-specific qualification matrix](PLATFORM_SUPPORT.md), the [release evidence packet](PERFORMANCE_AND_RELEASE_GATES.md) and all relevant validated scenario tests on the actual build being considered. Any unverified planned platform remains explicitly unqualified. Console/Apple expansion and online features require separate decisions and cannot be implied by a Linux package.

## 9. Scope and validation limits

- The architecture described here is a proposal for POLITIKA; documentation and faction artwork alone do not establish that corresponding Unreal modules or gameplay systems have been implemented.
- The chosen subsystem boundaries, simulation update model, gameplay mechanics and technical targets must be validated against actual prototypes and source code as development progresses.
- Before locking the design, test command latency, mixed-unit selection, pathfinding around blockers and bridges, gameplay-state serialization, and HUD usability at supported resolutions. Benchmark representative entity counts and frame-time budgets rather than assuming scalability.

This outline is a starting architecture contract, not a claim of implemented features or a locked strategic design.

## 10. Multi-platform architecture and acceptance

POLITIKA is a multi-platform product by design, not a Windows-first product with unspecified ports. The initial target set is Linux, Windows, SteamOS/Steam Deck-class handheld PCs, and Android. PlayStation, Xbox, Nintendo, and Apple systems are future candidates, subject to separate feasibility and support decisions. None of these targets is a claim of an existing executable or a certified release. The maintained target matrix and cross-platform requirements live in [Platform Support and Portability Plan](PLATFORM_SUPPORT.md).

- **Shared rules:** one portable RTS gameplay and mission simulation in C++ and data assets. No platform, store, controller or windowing API may control combat, resource, faction, mission or victory logic.
- **Input abstraction:** translate mouse/keyboard, handheld gamepad/Steam Input and Android touch gestures into the same validated selection and order intents; support focus/navigation without assuming hover or right-click.
- **Adaptive presentation:** preserve a 4K-capable desktop HUD while supporting handheld-readable controls, Android touch targets, screen safe areas, changed aspect ratios and density scaling. Mobile must not depend on desktop-only tooltips or precision-pointer gestures.
- **Packaging and local services:** keep save/config paths, system dialogs, device input, graphics APIs and platform distribution adapters isolated from the match rules. Offline campaign and skirmish must remain accessible without mandatory accounts wherever a build is offered.
- **Performance profiles:** separately define and benchmark PC high-resolution, handheld power/thermal and Android memory/GPU/thermal budgets. Scale VFX, textures, shadowing and UI without changing gameplay rule outcomes.
- **Qualification:** test real builds on representative Linux, Windows, SteamOS/Steam Deck and Android devices; confirm launch, menus, mission loop, readable HUD, input, save/load, resume, performance and graceful quit. Cross-play, shared cloud saves, release dates and storefront certification are outside the current commitments.

A single Unreal project with platform-specific targets and configurations is the desired direction. Validate actual Unreal/SDK/platform support, build-tool availability and device testing before locking packaging or release plans.

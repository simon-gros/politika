## Implemented boundary

The portable contract in `Source/PolitikaCore/Rules.h` now defines `CommandRequest`: match generation, local submission sequence, participant ID, runtime issuer ID, correlation ID, and one typed `Order` variant. These identities are separate. Authored definition IDs are not used as runtime command identities. Prototype entity IDs are allocated monotonically within the match and are not reused while it is active.

The match coordinator is the intake and admission authority. The player controller continues to resolve input intent and calls compatibility submission helpers; all five helpers now construct one typed request and enter `SubmitCommand`. Requests are queued in submission order and validated at the beginning of the next 0.05-second simulation step, against current coordinator state and the current weak Actor lookups. A destroyed/missing target is rejected; dead/unavailable issuers, stale match context, inactive matches and unauthorized participants are distinguished. A rejected request does not transition the unit order. An earlier valid request in the same queue remains effective if a later request is rejected. Successive accepted requests continue to replace the current order in queue order.

Unreal adapter capabilities now derive from configured movement speed and weapon properties, not the order being requested. Map coordinates in the portable request are 2D map-space offsets from the playable minimum; conversion to/from Unreal world coordinates occurs in the match adapter. Existing unit order enum and Actor mutators remain execution-state implementation details; only the coordinator dispatches admitted player requests to them. Development-only acceptance fixtures still set up scenarios directly and are not player command paths.

The coordinator retains the existing bounded accumulator: frame delta contribution is capped at 0.25 seconds, at most five 0.05-second steps run per rendered tick, and excess backlog is discarded after the five-step cap. The authoritative order remains admission, movement, combat resolution, damage, target/death cleanup, objective evaluation. This is repeatable local sequencing, not a cross-platform determinism claim.

## Structured event publication

The match coordinator now exposes `OnGameplayEventPublished()`, a native Unreal multicast delegate carrying a const reference to the portable `GameplayEvent` variant. It broadcasts each event synchronously at the existing final simulation publication phase, after the event is appended to the current-tick snapshot. Subscribers observe authoritative results only; they cannot mutate the event payload. A subscriber that retains an event after its callback must copy it. The existing `GetPublishedEvents()` snapshot remains available for the current rendered frame, while development logs remain diagnostic-only. UE Automation verifies a native subscriber receives the typed event; the packaged interaction replay verifies event categories against the authoritative development log. This is an in-process C++ observer surface, not a Blueprint, network, replay, save, or cross-platform determinism contract.

The development HUD subscribes to the match's native delegate and displays correlated accepted/rejected command outcomes from authoritative `CommandOutcomeEvent`s. It also renders an original five-row text/glyph command panel with current input hints and selected-unit capability styling. The panel is display-only; the final package screenshot records the selected unit, health, active order, objective and command rows. The HUD still uses the legacy last-feedback string for pre-admission cursor failures. Structured identity/localization fields, bounded/persisted history, and clickable rows remain deferred.

## Compatibility and next boundary

No save, content, world or network schema changed. The portable `Order` alternatives remain the canonical intent payload; UE’s `EPolitikaPrototypeOrder` remains only the current execution/presentation state. Legacy `SubmitMove`, `SubmitAttack`, `SubmitStop` and `SubmitGuard` adapters are retained and delegate to common intake. Typed events now drive HUD command outcome feedback; pre-admission input errors still use a presentation string. The HUD integration was build- and package-qualified in the Linux rendered Development interaction run; this does not qualify other platforms or physical displays.

**Network input (MP-1, 29 October 2026).** There is exactly one server-side intake, `APolitikaPrototypeMatch::SubmitControllerIntent`.
- **Who calls it.** A standalone or listen-host controller calls it in-process; a remote client calls it through the owning `ServerSubmitCommandIntent` reliable RPC. Both send the same versioned `FPolitikaNetCommandIntent`: order kind, issuer and target entity IDs, map-space destination, client sequence, correlation, generation hint and protocol version. It has no participant, owner or faction field.
- **Intake checks, in order.**
  1. Resolve the sender's server-side connection binding.
  2. Check `ProtocolVersion`.
  3. Consume the single-use `ClientSequenceGuard` sequence.
  4. `DecodeIntent` (bounded variant and shape, finite coordinates).
  5. Enforce the per-participant queue bound: 16 plus the participant's living units (`politika::selection::PendingCommandLimit`, capped by the 300-unit game limit), so a whole-selection group order fits ([group orders record](RTS_GROUP_ORDERS_4C_ACCEPTANCE.md)).
  6. Resolve entity IDs in the current match only.
  7. Enter the unchanged `SubmitCommand` → `AdmitPendingOrders` → `AdmitCommand` pipeline.
- **Teams and fog.** `AdmitOrder` now also treats allied targets as `FriendlyTarget`. Under networked fog it treats unobserved or unknown targets as `TargetNotVisible`.
- **Outcomes.** New rejection codes are appended: `MalformedCommand=15`, `DuplicateCommand=16`, `RateLimited=17`, `TargetNotVisible=18`. Outcomes go only to the issuing connection (`ClientReceiveCommandOutcome`).
- **Phase order.** The fixed-step order gains one read-mostly phase, team vision after movement and before combat. Offline it marks everything observed and does not change any existing event.

See the [MP-1 acceptance record](RTS_MULTIPLAYER_FOUNDATION_ACCEPTANCE.md).

The request accepts one issuer per call and is suitable for future per-entity dispatch. Multi-selection, formation semantics, group atomicity, AI and production remain deferred. The scoped Linux milestone is accepted; platform expansion, physical-device qualification and the follow-on multi-unit/formation milestone remain separate work.
